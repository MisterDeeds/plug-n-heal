# Ollama metadata blobs for Hugging Face models

Catalogue models with `"source": "huggingface"` in `src/catalog/models.json` are not in the Ollama registry, so a
drive cannot pull them from `registry.ollama.ai`. The builders ([`../Build-Drive.ps1`](../Build-Drive.ps1),
[`../build-drive.sh`](../build-drive.sh)) therefore download the two GGUF files from Hugging Face and copy the three
small metadata blobs below into `models/blobs/`, then write the Ollama-style manifest
(`manifests/registry.ollama.ai/<namespace>/<name>/<tag>`) themselves. The layout and the manifest are byte-for-byte
in the shape Ollama 0.40.15 produces for a registry pull, so Ollama reads the model offline without a pull.

The blobs are pinned here, in this repository, so that both builders (and the CI) work from the same bytes:

| File | Digest | Ollama layer it becomes |
|---|---|---|
| `config.json` (213 bytes) | `sha256:fd70fd02...f31b443` | the manifest's `config` (`application/vnd.docker.container.image.v1+json`) |
| `params.json` (92 bytes) | `sha256:448d2943...0b111` | `application/vnd.ollama.image.params` |
| `apache-2.0.txt` (11,345 bytes) | `sha256:4c6a8e84...17d1` | `application/vnd.ollama.image.license` |

`params.json` and `apache-2.0.txt` are **byte-identical to the Ollama registry layers** of the official Qwen models
(same digests), so a drive holding `qwen3.8:27b-q4_K_M` and `qwen3.8-27b-abliterated:q4_K` stores each of them only
once. `config.json` is the registry config of the official `qwen3.8:27b` with `file_type` set to `Q4_K` (one byte
shorter, hence the new digest); the GGUF itself and the other fields are unchanged.

These files are read verbatim, never regenerated by the builders. If they change, the digests in
[`../hf-models.json`](../hf-models.json) must change with them.
